# 修复 DeepSeek-OCR 文本框位置偏移 Spec

## Why

DeepSeek-OCR 返回的归一化坐标 (0-999) 转换为 PDF 坐标后，文本框显示位置向右上偏移，大小和位置不准确。

## 根因分析

### 调查结论

通过实际分析第 8 页 PDF（页面=1191.0x231.8pt, 图像=2482x483px@150DPI）：

| 项目 | 结果 |
|------|------|
| 图像在 PDF 中的边界框 | (0, 0, 1191.0, 231.8) — 完全覆盖页面 |
| 页面旋转 | 0° |
| PyMuPDF 坐标系 | Y=0 在顶部，Y 向下（与图像坐标系一致） |
| 渲染图像尺寸 | 2482x483 px |
| PDF 页面尺寸 | 1191.0x231.8 pt |
| 缩放因子 | 2482/1191.0 ≈ 2.084 px/pt (150 DPI / 72 DPI) |

### 关键发现

**之前的"白边导致坐标偏移"理论是错误的。**

原因：
1. `page.get_pixmap()` 渲染的是**整个 PDF 页面**
2. 渲染后的图像完全对应整个 PDF 页面（包括页面上的所有内容和空白区域）
3. DeepSeek-OCR 的归一化坐标 (0-999) 相对于整个渲染图像 = 相对于整个页面
4. 因此 `pdf = normalized / 999 * page_size` **应该是正确的**

白边是 PDF 页面本身的一部分（扫描件的白边就是页面内容），不存在"图像有白边但 PDF 页面没有"的情况。

### 待调查的真正原因

既然坐标转换逻辑本身是正确的，那么"向右上偏移"的真正原因可能是什么？

需要进一步调查：
1. **DeepSeek-OCR 返回的坐标本身是否有问题？** — 需要对比实际文本位置和返回的坐标
2. **图像在 PDF 中的绘制是否有变换？** — 检查是否有旋转、缩放等变换
3. **其他坐标转换问题？** — 检查是否有其他环节的坐标转换错误

## What Changes

- 删除错误的白边检测代码
- 重新调查文本框偏移的真正原因
- 根据真正原因实施修复

## Impact

- Affected code:
  - `modules/ocr/llm_extractor.py` — 删除白边检测调用
  - `modules/ocr/llm_response_parser.py` — 删除白边检测方法，恢复原有坐标转换逻辑
- Affected specs: `fix-llm-ocr-normalized-coords`

## REMOVED Requirements

### Requirement: 检测扫描图像白边

**Reason**: 白边理论错误。渲染图像完全覆盖 PDF 页面，白边是页面本身的一部分，不需要特殊处理。

### Requirement: 基于内容区域的坐标转换

**Reason**: 白边理论错误。归一化坐标直接映射到整个页面是正确的。

## ADDED Requirements

### Requirement: 调查文本框偏移的真正原因

需要收集更多证据来确定真正的原因：

1. **对比实际文本位置和 DeepSeek-OCR 返回的坐标**
   - 选择一个明显的文本块
   - 记录其在 PDF 中的实际位置
   - 记录 DeepSeek-OCR 返回的归一化坐标
   - 记录转换后的 PDF 坐标
   - 计算偏移量

2. **检查图像在 PDF 中的绘制情况**
   - 使用 PyMuPDF 获取图像的绘制矩阵
   - 检查是否有旋转、缩放等变换

3. **检查 DeepSeek-OCR 的坐标系统**
   - 确认归一化坐标 (0,0) 对应图像的哪个位置
   - 确认归一化坐标 (999,999) 对应图像的哪个位置

#### Scenario: 收集证据

- **WHEN** 分析第 8 页的某个文本块
- **THEN** 记录：
  - 文本内容
  - DeepSeek-OCR 返回的归一化坐标
  - 转换后的 PDF 坐标
  - 文本在 PDF 中的实际位置（通过可视化工具确认）
  - 偏移量（x, y 方向）

# 优化代码段特征描述（适配无换行符的输入） Spec

## Why

当前翻译提示词（规则10）中代码段特征描述包含"连续的多行缩进文本"和"特殊缩进结构"等描述。然而，提取阶段（2026-06-13）已统一删除所有换行符，到达 LLM 的文本是单行字符串，LLM 无法感知"多行"和"缩进结构"等信息，这些描述在当前的预处理流程下是过时且不准确的，可能导致 LLM 混淆或忽略代码段识别。

## 研究结论

经调查，换行符清理发生在以下路径：
- OCR 路径：`modules/ocr/paddle_extractor.py` `_build_text_from_textlines()` 第618行 `result.replace('\n', '')`
- 非 OCR 路径：`modules/pdf_extractor.py` 第428行 `text_block.block_text.replace('\n', '')`
- 表格路径：`coordinate_utils.py` / `table_processor.py` 中 `replace('\n', '')`

同时，`txt.strip()`（第596行）和 `' '.join(current_parts)`（第606行）也会剥离缩进空格，因此代码块的"缩进结构"特征同样丢失。

**输入到 LLM 的文本中仍然保留的特征**：编程关键字（`def`、`class`、`import` 等）和特殊符号（`=`、`{}`、`[]` 等），但"多行结构"和"缩进结构"不可用。

## What Changes

- **移除不准确的描述**：从规则10中移除"连续的多行缩进文本"和"及特殊缩进结构的文本"（输入中已不存在）
- **聚焦可靠特征**：仅保留编程关键字和特殊符号作为代码段识别特征
- **同时检查规则15**：确认规则15中"换行"描述是否需要调整

## Impact

- Affected code: `modules/translator.py` 的 `_generate_system_prompt` 方法（第150-154行）
- 行为变更：LLM 收到的代码识别特征更准确，减少误导
- 影响范围：所有翻译请求（提示词变化影响 LLM 行为）

## MODIFIED Requirements

### Requirement: 修改规则10的代码段特征描述

修改 `modules/translator.py` 的 `_generate_system_prompt` 方法中规则10的第三项代码段识别特征说明。

当前文本（不准确，包含已不存在的特征）：
```
    - 代码特征识别：连续的多行缩进文本、包含常见编程关键字（如 `def`、`class`、`import`、`if`、`for`、`function`、`var`、`const` 等）、特殊符号（`=`、`=>`、`->`、`<>`、`()`、`{}`、`[]`）及特殊缩进结构的文本，应识别为代码段处理；
```

修改后文本（移除过时的"多行缩进"和"缩进结构"描述，聚焦实际存在的特征）：
```
    - 代码特征识别：包含常见编程关键字（如 `def`、`class`、`import`、`if`、`for`、`function`、`var`、`const` 等）或特殊符号（`=`、`=>`、`->`、`<>`、`()`、`{}`、`[]`）的连续文本片段，应识别为代码段处理；
```

#### 变更点对比

| 原文本 | 变更原因 |
|--------|---------|
| `连续的多行缩进文本、` | **移除** — 输入中无换行符，无"多行" |
| `...常见编程关键字...` | **保留** — 该特征在输入中存在 |
| `...特殊符号...` | **保留** — 该特征在输入中存在 |
| `及特殊缩进结构的文本，` | **移除** — 缩进在提取时已被 strip 和 join 剥离 |
| `应识别为代码段处理；` | **保留** — 语义不变 |

### Requirement: 检查规则15是否受影响

规则15：
```
15. **保持列表格式**：原文中的列表格式（换行、项目符号如•、-、数字编号等）必须在翻译结果中保持，不将列表项合并为连续段落。
```

分析：规则15前半句"原文中的列表格式（换行）"虽同样面临输入无换行符的问题，但规则15的核心目的是**约束输出格式**（翻译结果保持列表不合并为段落），而不是要求 LLM 在输入中检测换行符。只要 LLM 识别出列表项模式（如项目符号、数字编号），就应在输出中保持列表结构。因此规则15**不需要修改**。
